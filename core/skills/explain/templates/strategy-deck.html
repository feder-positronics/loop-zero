From push-all to search-first: IntelFlo's pipeline migration

We're shifting from a pipeline that pushes every datafeed item into a user's inbox, to a model where users search the state of the knowledge on demand — while feeds keep dropping new content into the inbox only for the alerts and sources users have explicitly registered.

The decision

Migrate IntelFlo's content pipeline from a push-all-to-inbox model to a search-first model in which:

  • The primary surface for "what do we know about X?" is a query against a unified search layer that spans both the internal IntelFlo archive and external sources (e.g., OpenAlex, PubMed).
  • Datafeeds still deliver new content to the inbox — but only items that match a user's registered alerts (saved searches) or come from registered sources (feed subscriptions). All new content is still indexed so search can find it later; only registered matches reach the inbox.
  • The inbox becomes scoped to what the user explicitly asked for — alerts and source subscriptions — rather than the default firehose.

Two mental models

Core idea

In the old model, the system pushes everything it finds and the user filters from a firehose. In the new model, the user pulls what they need via search, while the inbox is reduced to the targeted alerts and source subscriptions the user has registered.

Mechanism — old: push-all-to-inbox
  1. Datafeed publishes new items (RSS, API, scheduled crawl).
  2. Pipeline normalizes, enriches, indexes.
  3. Every matched item lands in the user's inbox.
  4. User triages: read, save, dismiss, ignore.
  5. "State of the knowledge on topic X" is implicit in the inbox stream — never queried directly.
Mechanism — new: search-first
  1. User issues a query: "what do we know about topic X?"
  2. Search layer queries both internal archive and external sources in one pass.
  3. Results are ranked, deduplicated, and presented with provenance and uncertainty labels.
  4. Datafeeds keep running. All new content is indexed so the search layer can find it later.
  5. New items also land in the user's inbox — but only if they match a registered alert (saved search) or come from a registered source subscription. Everything else is searchable but not pushed.

Three options considered

Option What it is Best for Failure mode
A. Status quo Keep push-all-to-inbox. Improve filtering and triage UX. Users who want to be alerted to everything. Attention overload; "state of the knowledge" stays implicit and hard to query.
B. Pure search Drop the inbox. Everything is on-demand search. Power users with clear queries already in mind. Users miss genuinely-new important content; no proactive surface.
C. Hybrid (recommended) Search is primary. Feeds signal updates and trigger reindex. Inbox becomes an opt-in, opinionated notification surface for explicit subscriptions. The realistic mix: people both query and want to be told when something material changes — but only for things they care about. Two surfaces to maintain; trust-ranking complexity (the #198 problem) becomes load-bearing.

Trade-offs

Coverage vs. relevance

Push-all maximizes coverage at the cost of relevance. Search-first maximizes relevance at the cost of "you didn't ask, so we didn't show you."

Latency

Push pre-indexes everything; user reads from a primed inbox. Search-first runs queries on demand — latency must be tight, or perceived value drops fast.

Discoverability of new content

Push surfaces new items by default. Search-first relies on the user having registered what they care about — alerts (saved searches) and source subscriptions — so the inbox can still surface "what's new" for those targeted slices. Anything outside the registered set is searchable but not pushed.

Trust ranking

Push lets the user rank as they go. Search-first must rank at query time across heterogeneous sources (internal vs. OpenAlex vs. PubMed vs. user-curated archive). This is the load-bearing hard problem; the recent #198 reopen elevated it explicitly.

Migration cost

Existing inbox content, existing pipelines, existing user workflows. Cannot flip overnight without losing institutional memory or breaking habits.

Recommendation

Adopt Option C — hybrid, search-first. Reasoning:

  1. The "state of the knowledge" question is the actual product. Users want to know what's known about a topic; an inbox is a poor surface for that question. Making search primary aligns the system with the dominant user job.
  2. Feeds keep delivering to the inbox — but only for what the user explicitly asked for. Registered alerts (saved searches) and source subscriptions still flow to the inbox; everything else is indexed for search but not pushed. The firehose is gone; the targeted delivery survives.
  3. The hybrid preserves a proactive surface. Users who want "tell me when X happens" register an alert; users who want "follow these specific sources" subscribe. The inbox surfaces those — and only those — instead of everything that crosses the pipeline.
  4. The architectural cost is concentrated in trust ranking — which is already a reopened blocker (#198). Investing there pays off regardless of which option we pick.

Risks and uncertainty

Known Trust ranking across internal + external sources is hard and is already a reopened blocker (issue #198 plus children #488–#491: API scope, trust ranking, enrichment ladder, vectorization tiering).

Known OpenAlex external usage must stay within the free tier; this bounds the enrichment ladder.

Likely Search latency will need a target SLA (e.g., <1s p95) for the model to feel right. Without it, users may default back to the inbox they remember.

Likely Onboarding to "what to register" — alerts and source subscriptions — becomes a load-bearing UX moment. If users don't know what to register, the inbox underdelivers and they drift back to wanting the firehose.

Uncertain The migration sequencing — which pipelines and feeds flip first, what happens to existing inbox content during the transition, how existing implicit subscriptions are mapped to explicit registered alerts and sources.

Uncertain Whether the existing push pipeline can be reshaped into the dual-path model (index for search + scoped delivery for registrations) or whether a parallel system runs during transition.

Speculative Long-term, the search-first model may make agent-driven synthesis (the substrate + agents + steering-UI vision) easier, because agents read from the same search layer that users do. Compositional value, not yet validated.

Open questions

  1. What's the latency target (p95) for a search query that spans internal archive + external sources?
  2. How does an inbox subscription map to a notification rule in the new model?
  3. Can the existing push pipeline be reshaped into the dual-path model (always index for search; scoped delivery only for registered alerts/sources), or does the delivery path need a parallel build during transition?
  4. What's the rollout sequence — per-feed, per-user, per-cohort?
  5. How is "freshness" surfaced in search results (sort order, visual marker, separate "what's new" view)?
  6. Does trust ranking ship before, during, or after the surface flip?

Glossary

Datafeed
A source of upstream content (RSS, API, scheduled crawl). In the new model, datafeeds continue to deliver — but only items that match a registered alert or come from a registered source. All new content is also indexed so search can find it later.
Inbox
The per-user firehose surface in the current model. In the new model, the inbox is scoped to registered alerts (saved searches) and registered source subscriptions — the user gets only what they explicitly asked for.
Registered alert
A saved search the user has chosen to be notified about. When a datafeed item matches the alert, it lands in the user's inbox.
Registered source
A feed (or other upstream source) the user has explicitly subscribed to. New items from that source land in the inbox; items from unsubscribed sources do not.
Search layer
The unified query surface that spans the internal IntelFlo archive and external sources (OpenAlex, PubMed, etc.) in one pass.
Trust ranking
The ordering of heterogeneous results (internal archive items, peer-reviewed papers, preprints, blog posts) by relevance and credibility. The load-bearing hard problem of the search-first model.
Substrate
IntelFlo's deterministic data layer — the indexed, normalized, archived content. Distinct from agent-driven synthesis on top.
